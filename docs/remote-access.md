# Browser remote access

The browser client shares the desktop session and business API. Electron owns LAN HTTP and relay HTTPS connections; the Go daemon binds loopback and requires its startup token on every `/remote` route. A phone credential never replaces this startup token.

SQLite schema v32 owns a random stable `desktopID`, one-time authorization codes, and device grants. Identity follows the daemon data home (`~/.pudding-dev` or release `~/.pudding`); relay registration does not own identity. Provider YAML remains the source for `/remote/models`, which returns configured provider/model IDs and labels without secrets.

1. The local desktop issues an authorization QR code through startup-token-guarded `POST /remote/pairings {mode,origin}`. Creating this code authorizes one browser to connect as the owner. The eight-character Base32 code is returned once; only its SHA-256 hash is stored, and it expires after five minutes.
2. The browser submits the code to the gateway. The client supplies the automatic device label `Browser device`; the gateway injects its exact mode and origin. LAN uses an HTTP IPv4 origin derived from the selected listen address and port; relay uses an HTTPS origin.
3. `POST /remote/pairings/request {code,deviceName,mode,origin}` consumes the matching unexpired code and creates a 30-day device grant in one transaction. It immediately returns `{token,device}`. Only the token hash is stored. Losing the response requires issuing a new code; the consumed code cannot recover the credential.
4. Gateway stores the token in a mode-specific HttpOnly SameSite cookie (Secure for HTTPS relay), removing the token from the public response. There is no phone name form, pending approval, or polling step.
5. Gateway authenticates every business request through `POST /remote/authorize {token,mode,origin}` and applies its explicit owner-business allowlist. A valid scope that does not match the credential, or an expired/revoked token, returns 401. `DELETE /remote/devices/{id}` revokes the grant immediately.

`GET /remote/access` returns `{desktopID,devices,pairings}`, with RFC3339 timestamps and non-null arrays. Each unclaimed pairing is `{id,mode,origin,expiresAt}`; no status or requested-device fields remain. The local desktop can cancel an authorization code with idempotent `DELETE /remote/pairings/{id}`. Invalid scope/name returns 400; invalid, consumed, canceled or expired codes return 401. Scope origins have no credentials, path, query, fragment or trailing slash. LAN accepts HTTP IPv4 origins (loopback included for tests); relay requires HTTPS. Changing a LAN address or port requires a new code and registration.

Schema migration v31→v32 discards only old short-lived pairing rows: these codes were issued under later-desktop-approval semantics and must not become preauthorized. Identity, existing device grants, sessions and canonical messages are preserved. The migration is transactional; failure preserves v31 rows and version, and retry after restart upgrades normally. Schema v31's published fingerprint and migration remain unchanged.

`GET /remote/events` is a startup-guarded resource authentication invalidation stream. It starts with `remote.ready {}`, followed by `remote.changed {deviceID?,pairingID?}` after successful mutations. It owns no credential facts and is not conversation history. On reconnect the gateway reauthorizes active streams; device invalidations cause closure/rechecking, while code-only changes do not invalidate existing devices. Slow subscribers disconnect rather than miss invalidations. Expiry is enforced from canonical timestamps on each authorization and on active stream lifetimes. Session SSE keeps its existing sequence and replay semantics.

Protocol 15 removes `/remote/pairings/{id}/poll`, `/approve`, `/deny` and their DTOs. No old pairing API compatibility path remains.
