# 审批与命令执行优化方案

> 状态：待实施设计，2026-09-16。
> 代码基线：`720699ff9de825919478fd04a47243f05a427b6e`；已包含 PR #6 的命令分类修复和本地预览设计文档。
> 本文只提出后续设计，不表示审批、只读沙箱或任务授权已经实现。

## 1. 目标与推荐路线

目前通过不断补充命令、参数和 Shell 特例来决定是否自动执行，维护成本持续增加。根本问题是：能识别一条命令的表面结构，并不等于能证明它及其子进程没有写入、联网或其他副作用。

推荐保留 Go daemon、Electron 和现有 `CommandRunner`，按以下顺序推进：

1. **收紧 Shell 自动执行，自动运行的通用 CLI 默认只能读取原项目。** 写入仅开放给隔离临时目录和构建缓存；自动命令默认不联网。
2. **审批基于同一份执行计划和资源边界。** 分析器负责解释和识别需要确认的操作，操作系统负责限制实际访问。
3. **复用已有结构化文件、Patch 和 Git 工具。** 常见检索、文件操作与 Git 查询优先使用明确契约；普通程序直接传 executable + argv；复杂 Shell 显式审批。
4. **随后增加有界授权复用与隔离任务副本。** 减少同一任务反复弹窗，最终允许在副本内完成修改和验证，审阅差异后回写原项目。

第一阶段预计 **6–10 人日，单人约 2 周**。任务授权、隔离副本和替换沙箱运行时分别实施，不作为首期前置条件。

当前行为以代码为准；[Code CLI 沙箱设计](code-cli-sandbox-design.md) 是现行参考，[Code 能力计划](code-capabilities-plan.md) 和 [CLI-first 收敛计划](code-cli-first-consolidation-plan.md) 是已完成的历史记录。

| 项目 | 当前真实行为 | 本次设计的变化 |
| --- | --- | --- |
| Shell 分析 | 已使用 `mvdan.cc/sh/v3 v3.13.1` 的 POSIX AST，结合命令、参数、环境和路径规则分类 | 继续复用解析器，缩小其承担的自动放行证明范围 |
| 命令入口 | `builtin_command_run` 接受 `command`，macOS 最终使用固定 `/bin/sh -c` | 普通执行增加明确的 executable + argv 表示，保留有真实用途的 Shell 执行 |

| 网络 | 当前 SBPL 允许出站网络，联网风险主要由命令策略控制 | 首期增加由 runner 强制的“禁用网络 / 允许出站”选择；域名控制后置 |
| `ask / auto / full` | ask 豁免低风险只读；auto 对 read 类直接通过，其他调用按风险；full 跳过一般审批并绕过命令沙箱 | 保留三档名称，明确资源范围与是否弹窗是不同维度 |
| 结构化修改 | Patch 已有审批快照和漂移校验；Git 写入已有显式路径、HEAD/index 校验与 hooks/filter 限制 | 保留已验证能力，不随通用 CLI 一起改成只读 |
| 临时授权 | Code 的 turn 目录授权保存在内存；session 目录授权会创建、绑定或扩展持久 Project | 后续把可复用任务授权与持久项目目录分开 |
| 命令授权复用 | 普通调用批准只释放该次调用；仅受限 Chrome 截图有严格的会话复用规则 | 不把截图特例扩大成任意命令前缀授权 |
| 审批恢复 | daemon 存活时，页面可通过 session 快照恢复待审批项；daemon 重启后不能继续原待审批执行 | 首期明确失效，持久恢复与任务系统合并设计 |

[PR #6](https://github.com/teatak/pudding-core/pull/6) 已修复 Git branch/tag 查询选项边界、等号形式参数误判，以及未加引号变量展开和 `OLDPWD` 的静态判断问题，并加入真实 Git 副作用与 macOS Shell 回归。它们是本方案的基线，不能重复列为尚未修复的问题。

例如，`git branch --sort refname newbranch` 可能创建分支，`--sort` 本身不代表查询；`git branch --contains=HEAD` 则是查询形式。后续仍保留这些测试，但不再试图靠穷举所有程序选项保证原项目不被修改。

## 3. 范围与现有设计的关系

本次重点覆盖 LLM 发起的 Code 命令、前后台执行、相关审批展示和临时资源授权。继续保留 Core + session 按需加载 App 的工具组织，不恢复已删除的 `project_inspect`、`project_instructions`，不新增功能重复的检索工具。

新方案实施时，将替代现行“未知直接命令可在可写项目中自动执行”以及历史 CLI-first 计划中“单一 command 字符串承担所有执行”的策略；同步更新当前沙箱文档、工具 schema、prompt、展示和调用方。Shell 与直接执行是两种明确任务语义，共用一个准备、审批和执行流程，不维护新旧审批器并行的兼容路径。

**“原项目只读”只约束自动通用 CLI。** 现有结构化文件写入、Patch 和 Git 写入继续按各自契约运行；用户明确批准的命令可获得本次调用所需的项目写权限。这是隔离副本完成前的过渡能力，批准不自动变成 host access。

用户手动使用终端、打开本地 HTML 的行为继续由对应桌面入口处理。[本地预览与链接方案](local-html-preview-and-links-design.md) 已规定，手动打开任意可读 HTML 不应要求先绑定项目。浏览器预览的授权不会授予 CLI 写入权，CLI 授权也不会绕过浏览器资源校验。模型调用需要的授权必须来自可信执行链，不能由工具参数自报“用户操作”。

本设计不直接沙箱化整个 Electron/daemon、LSP 或所有 App/MCP，也不把普通读取分类当作这些工具访问任意资源的许可。

## 4. 同一份执行计划贯穿审批与运行

沿现有 tool call 生命周期生成一次规范化执行计划，交给策略、审批卡和 runner 消费。它是该次调用的权威快照，不新增独立的全局权限状态。

| 内容 | 约束 |
| --- | --- |
| 调用身份 | 使用现有 `sessionID / turnID / callID`；前后台一致，不读取前端选中会话 |
| 命令表示 | 直接执行保存 executable 与独立 argv；Shell 保存原始脚本和固定解释器；两者互斥 |
| 执行上下文 | 固定解析后的可执行路径、cwd、最终受控 env、超时、background、tty 和 stdin 能力 |
| 文件边界 | 分开记录可读目录、可写目录以及必要的拒绝项；解析真实路径并检查重叠 |
| 网络边界 | 明确禁用或允许出站；域名级约束只有 runner 能执行时才提供 |
| 决策依据 | 保留需要确认的实际操作、资源扩展原因和解析不确定性，不能只用一个 `LowRisk` 布尔值表达全部含义 |
| 授权依据 | 记录本次批准或有效临时授权的来源与范围；前端只展示后端事实 |

审批后执行原计划，不让模型重新生成另一条“等价命令”。cwd、env、参数、目录边界、执行模式或可执行文件身份发生变化时，旧批准不得覆盖新计划。使用既有 Patch/Git 漂移校验的原则，实施时确定并测试可执行文件与资源快照的校验方式；路径字符串相同不等于文件未变化。

对普通程序使用直接 exec，参数中的空格、`$`、引号、换行和 `*` 作为参数内容处理，不再拼成 Shell 字符串。需要管道、重定向、条件和变量展开时明确选择 Shell。

首期对复杂 Shell、解释器内联代码和无法确定的展开仍要求确认。可可靠还原为单个字面量调用的 Shell 输入可以归一成直接执行；不为减少弹窗模拟完整 Shell 运行环境，不给未知展开填入看似安全的占位值。

直接 argv 只减少解析歧义，不能证明程序只读；`npm test`、`go test`、项目脚本和未知二进制都可能运行子进程或修改文件，仍必须受到实际资源边界限制。

## 5. 首期资源策略与审批语义

### 5.1 文件与网络边界

自动通用 CLI 的默认执行范围：

- 原项目目录可读，包含原项目的 Git 元数据；不允许创建、修改、删除、重命名或修改权限。
- Pudding 管理的隔离临时目录和构建缓存可写，继续复用现有环境准备与缓存机制。
- 系统运行库、解析出的工具链目录继续按现有只读规则开放；不因此开放用户配置和凭证。
- 网络默认禁用，由 Seatbelt 阻止真实连接和监听，不能只检查 `curl` 等命令名或设置代理环境变量。
- 需要项目写入或联网时，生成展示具体变化的新计划；批准后只扩展该次调用，保持其余边界。
- 沙箱不可用、规则生成失败或授权范围无法实现时，执行失败；不能静默改用 full 或 host 重跑。

只读项目与可写缓存不能因父子目录重叠而扩大权限。例如项目误设为用户主目录、临时目录包含项目、软链接指回项目时，应拒绝不明确的配置或生成可验证的更具体限制，不能依赖规则顺序猜测结果。测试必须覆盖 rename、删除、符号链接和硬链接写入等真实效果。

首期网络只有“禁用”和“允许出站”两种可实现能力。允许出站时保留当前本地监听约束，并明确现有 Seatbelt 对通配绑定的限制；不能展示尚未实施的“仅允许某域名/端口”。不提供只配 HTTP proxy、仍可直接联网的伪隔离。

联网批准要展示“可向外发送此进程能读取的数据”。文件只读解决原项目完整性，不解决数据外发；即使后续有域名列表，也不能据此证明网络操作只有下载、没有上传。

只读、离线程序仍会消耗 CPU/内存、写入或污染获准的缓存，也可能长期在后台运行。首期沿用现有前台超时、后台进程数量限制和停止入口，不承诺 CPU、内存或磁盘硬配额。

### 5.2 行为矩阵

下表描述首期完成后的目标，不是当前运行行为：

| 场景 | ask | auto | full |
| --- | --- | --- | --- |
| 已验证的结构化只读调用，资源在有效范围内 | 按当前低风险只读豁免 | 自动 | 自动 |
| 普通直接命令，默认只读、离线边界内且无必须确认的操作 | 逐次审批 | 可自动执行，副作用由沙箱限制 | 按当前完整访问语义执行 |
| 复杂 Shell、解释器内联代码、动态展开、交互 stdin/TTY 或明确破坏性操作 | 逐次审批 | 逐次审批 | 不弹一般审批 |
| 通用 CLI 请求写入原项目 | 展示目录范围后批准 | 展示目录范围后批准 | 完整访问 |
| 通用 CLI 请求联网 | 展示实际网络能力后批准 | 展示实际网络能力后批准 | 完整访问 |
| 项目外资源或 host access | 显式申请，不随一般批准附赠 | 显式申请，不随一般批准附赠 | 按当前完整访问语义 |
| 结构化 Patch、文件与 Git 写入 | 保持各自现有审批规则 | 保持各自已验证的自动执行和风险规则 | 仍执行路径、内容与漂移校验 |

`full` 继续表示用户主动选择的完整访问模式。它不用于消除沙箱失败提示，也不因一条命令获批而写回 Project 审批模式。

阶段变化会影响当前可自动执行的构建、测试、依赖下载和开发服务：需要写项目或联网的任务可能先遇到明确限制。应优先使用受控缓存或现有结构化工具；确实需要扩大权限时，说明真实需求并请求本次批准。不能静默删掉命令步骤、改写任务，或用 host 执行掩盖不兼容。

## 6. 有界授权复用与审批交互

首期保留调用级批准；下一阶段用资源范围减少重复审批。复用的是已经批准的用途和边界，不是 `git *`、`python *`、`npm *` 等命令前缀。

| 授权范围 | 生命周期与约束 |
| --- | --- |
| 本次调用 | 只消费已展示的计划；不产生后续调用豁免 |
| 当前 turn | 仅同一 session/turn、批准资源和用途内复用；结束、取消或撤销后不再启动新操作 |
| 当前任务 | 任务系统落地后绑定真实 task run；有截止条件和撤销入口，不用 session 冒充任务 |
| 专项 session 授权 | 仅明确实现和测试过的用途；已有 Chrome 截图规则继续独立验证，不自动泛化 |

首期不增加“永久允许此命令”。后续通用临时目录授权也不写入共享 `Project.RootDirs`；只有用户明确配置持久项目目录时才修改 Project。当前 `request_capability` 的 session 目录授权会持久扩展项目，这一行为若调整必须同步迁移契约和 UI，不能只改文案。

审批卡先显示用户能判断的内容：

- 要完成的动作，例如“运行构建并写入 dist”，以及为何需要新增权限。
- 实际命令、工作目录、读写范围、网络能力和前台/后台运行方式。
- 本次批准的期限；明确是否允许后续交互输入、是否需要离开沙箱。
- Patch 与 Git commit 继续展示现有差异和漂移校验结果；环境按敏感字段脱敏，不在卡片或日志暴露凭据。
- 默认操作为“允许本次 / 拒绝”；只有后端提供真实、可验证的复用范围时才展示对应按钮。

前台、后台和 TTY 使用相同的启动计划。首期把可交互 stdin/TTY 作为显式启动能力，在 ask/auto 下启动即审批，批准覆盖该进程后续输入；默认自动后台进程仅允许读取输出和停止，不允许用 `command_session.write` 临时取得交互能力。这样不会出现先自动启动空的 Shell/解释器、再输入脚本来绕过复杂代码确认的路径，也无需持续枚举解释器名称。

后台 `command_session.write` 会继续向已获交互授权的程序输入，不能描述成仅批准了第一条命令；host 交互 Shell 的后续输入具有该进程的完整权限，必须明确展示，不能复用普通只读调用的批准。只读、离线的交互进程同样遵守上述确认规则和原有资源边界。

权限在进程启动时固定。取消 turn 或撤销复用授权会阻止新的调用，不自动改变已运行后台进程；UI 显示仍运行的进程并提供现有停止入口。用户选择停止时终止进程组。不要承诺修改 Project 或关闭审批卡即可收回既有进程权限。

同一调用的重复批准、迟到批准、其他 session 的批准必须幂等处理或拒绝，不能启动第二份进程。授权检查、消费和启动要有明确的竞态处理，执行前不能重新读取一个已扩大范围的全局项目配置。

## 7. 恢复、状态与审计

继续使用后端 session 快照和事件驱动前端，审批 overlay 不成为权限事实源。daemon 存活时，刷新页面应恢复已有待审批项，不重新创建调用。

首期不承诺 daemon 重启后继续执行：原待审批计划和内存授权失效，按现有恢复流程结束未完成 turn；旧审批按钮不能重新触发动作。后台进程也不承诺跨 daemon 重启恢复。

需要任务级等待与重启恢复时，与 [任务系统设计](tasks-design.md) 的审批记录、状态转换和执行恢复一起实现。只保留一份待审批权威记录；批准、拒绝、取消、过期与任务状态应协调提交。恢复时重新校验资源与执行计划，不把数据库里一个“已批准”字段直接当成仍有效的系统权限。

具体遵循任务设计 §9.3：原 Turn 的未决审批在重启后失效，用户明确重试时创建新 Run；已批准但不确定是否执行的操作先核对真实结果，不自动重放。持久化解决记录恢复和可控重试，不承诺恢复原调用栈。

审计记录围绕 call/process 标识，记录请求了什么范围、谁通过可信入口批准、实际使用何种沙箱、最终是否执行成功。不要持久化完整进程环境或凭据；审批统计只需要结构化原因与结果。

## 8. 后续隔离副本与差异回写

更完整的自动化目标是在任务副本中允许写入，原项目只在用户审阅后由受控回写修改。该阶段预计 **12–20 人日**，不等同于创建一个 worktree 就完成隔离。

C 阶段先支持普通交互会话，副本、产物和进程以现有 session/turn 记录归属，可跨后续 turn 审阅；不依赖完整 Task/Run 系统，也不创建虚构的任务实体。这里的“任务副本”指用户当前工作请求的隔离执行目录。

[任务系统设计](tasks-design.md) §6.2 对手动、定时和外部触发的 Task/Run 另有约定：从确定 commit 创建 worktree，不自动携带主工作区未提交修改。C 的交互副本需要保留当前工作上下文，不能直接改变这项任务基线。后续接入 Task/Run 时继续采用其干净 commit 语义；若选用本节的独立副本替代 linked worktree，必须同步修订任务文档的物理工作区方案，不能让两个方案对同一 Run 并行生效。

需要同时解决：

1. **创建副本。** 明确纳入的已跟踪文件、未提交修改和未跟踪文件，建立源文件指纹；不把缺失内容当作空文件。排除项要可见，不能静默漏掉任务依赖。
2. **隔离实际存储。** 不使用会联动原文件的可写硬链接。Git linked worktree 共享 common dir，不能直接当成独立 Git 元数据；首版优先独立副本，或另行证明共享元数据的限制。
3. **执行与检查。** 在副本中运行模型修改、测试与构建，产物和进程归属创建副本的 session/turn；接入任务系统后再关联真实 Run。文件隔离不隐含联网许可，网络与凭据单独处理。
4. **生成可审阅差异。** 明确展示新增、修改、删除及不能自动回写的文件类型；不能只展示截断后的 patch 却批准全部内容。
5. **校验并回写。** 复用现有 Patch/Git 的快照与漂移思路。原项目变化时拒绝或明确解决冲突，不能覆盖用户的新修改；失败时避免部分应用。
6. **清理与追溯。** 先停止相关进程，再回收副本；保留任务结果和必要差异，不把临时副本路径写成持久项目事实。

发布、推送和对外系统写入不能通过“本地差异已批准”自动获权。任务授权还需要表达这些实际外部操作。

## 9. 开源项目的使用方式

以下外部资料于 2026-09-16 核对，供实现选型；本次文档没有引入新依赖。

| 项目 | 可使用的部分 | 对本项目的建议 |
| --- | --- | --- |
| [mvdan/sh](https://github.com/mvdan/sh) | Shell parser、formatter、interpreter；仓库已经依赖其语法解析库 | 继续使用 AST；不把解释器当作安全证明器，不再另造 Shell parser |
| [Anthropic Sandbox Runtime](https://github.com/anthropics/sandbox-runtime) | 基于原生系统机制的文件限制和代理网络控制，提供 CLI 与库 | 作为后续替换 runner 或引入域名控制的候选；先做与 Pudding 权限契约的适配验证 |

Anthropic Runtime 的 macOS 路径仍使用 `sandbox-exec`，替换它不会消除对 Seatbelt 的依赖；其文档仍将接口列为预览阶段。它的文件读取默认和例外优先级也不能直接照搬为 Pudding 的授权规则。应明确映射有效目录、网络和 IPC 范围，并验证整个进程树、取消和多会话隔离。参见其[实现与隔离说明](https://github.com/anthropics/sandbox-runtime#how-it-works)。

**建议首期不改接外部 runtime。** 当前已有可替换的 runner 和原生回归基础，先完成可度量的边界收敛。若后续需要域名代理和更广平台支持，再单独安排 **6–10 人日**的适配估算；实际排期取决于选定版本、打包、代理生命周期和桌面验收结果。

## 11. 验收与回归方法

验收必须观察实际副作用，不能只断言分析器返回了 `LowRisk=false`。所有文件、Git 仓库、进程和数据库 fixture 使用临时目录。

| 类别 | 必须验证的结果 |
| --- | --- |
| 当前修复保留 | PR #6 的 branch/tag 选项、参数形式、未加引号展开与 macOS 原生 Shell 用例持续通过 |
| 自动命令只读 | 临时程序尝试写入、删除、rename 原项目和 Git refs 均失败，项目与 refs 前后内容不变；同一程序可写入授权的隔离临时目录 |
| 任意子进程 | 项目脚本、未知二进制、解释器及其子进程都继承同一文件/网络限制，不靠命令名称判断测试成功 |
| 路径边界 | 绝对路径、`..`、软硬链接、读写目录重叠、cwd 或目标替换不能扩大范围；无法保证时明确失败 |
| 网络 | 离线模式下真实外连、loopback 连接与监听被拒绝；批准出站后按展示边界生效，结束后后续调用不能继承 |
| 参数与漂移 | 空格、中文、引号、换行作为 argv 保真；批准后修改计划、环境、执行目标或项目绑定不能使用旧授权 |
| 前后台与交互 | 同一命令前后台资源结果一致；交互能力启动即确认，自动后台进程不能后补 write 权限；stdin/TTY 不超出启动授权；poll/write/stop 不能访问其他 session |
| 结构化写入 | Patch 原子性、源文件漂移、Git HEAD/index 漂移、hooks/filter 限制与现有 ask/auto 行为保持 |
| 审批生命周期 | 拒绝和取消不启动；重复/迟到/跨 session 批准不重复执行；网页恢复待审批，daemon 重启后旧批准失效 |
| 失败恢复 | 沙箱失败不 host 重试；构建缺少写入或联网权限时展示准确原因，不伪报测试通过 |

保留分类单测和已有真实 Git/macOS 回归，再补能证明资源隔离的执行用例。POSIX Shell 的关键行为必须在 macOS `/bin/sh` 上验证，不能用 Linux 的环境继承结果代替原生结论。

实施后的检查入口按改动选择：`go test -tags 'sqlite_fts5 webrtcaec' ./internal/tool ./internal/engine ./internal/api`，`npm --prefix web test`、`npm --prefix web run build`；涉及 Electron 时补 `npm run test:electron` 和真实桌面回归，涉及持久结构时补 `make schema-check`。本次只写文档，不声称这些实现验收已经运行。

## 12. 判断优化是否有效

固定一组项目任务，比较实施前后的结果：搜索和阅读、结构化 Patch、Git 查询、测试构建、依赖下载、开发服务、后台交互、拒绝后继续工作。记录任务完成率、审批次数、重复权限请求、沙箱拒绝原因、人工介入次数和总耗时。

首期的硬门槛是自动通用 CLI 无法写坏原项目、批准不能扩大到另一调用、前后台边界一致，且已有结构化编辑流程可用。复杂 Shell 的提示数可能先增加；B 阶段再验证同一已授权用途不反复询问。审批数下降只有在任务完成率和资源边界保持的情况下才算改善，不能通过默认 full 或隐藏失败达到指标。
