# 定时任务：首版实施计划

> 日期：2026-09-21。状态：首版实现与本地验证已完成；未发布。
> 跨仓唯一实施文档：core 负责定时规则、持久化、调度和公共协议；desktop 负责独立菜单、任务管理、会话卡片和系统通知。
> `internal/`、`contracts/` 相对 pudding-core；`web/`、`electron/` 相对 pudding-desktop。
> 本文取代 [旧任务草案](tasks-design.md) 作为本轮实施依据。旧草案仅保留用于追溯，其外部 Agent、结果审查和 callback 不纳入本次范围。

## 1. 产品目标与范围

在指定时间，将预先保存的任务指令提交到关联会话，按该会话现有的执行、排队、审批和补充输入规则处理。用户可以从独立的「定时任务」菜单统一管理计划，也可以在会话中用自然语言创建。

首版包含：

- 一次性指定时间／延迟执行，以及每天、每周重复。
- 自然语言创建；菜单中的新建、搜索、修改、暂停、恢复、立即执行和删除。
- 绑定原会话、触发记录、跳转对应执行位置、系统通知。
- 时区、重复触发去重、同任务不重叠、休眠／退出后的错过处理、重启对账。

首版不包含：固定分钟间隔、复杂 cron、依赖工作流、云端执行、系统唤醒、外部 Agent 接入、跨会话委派、独立结果审查、自动返工、独立 worktree 和任务专属预算系统。每次触发不新建 Session，不增加新的会话模式。

“已执行”表示对应执行链已经结束，不代表系统独立验收了业务目标；提交成功、排队成功不能显示为执行完成。

## 2. 已确定的交互

### 2.1 独立菜单

左侧主导航在「项目」附近增加「定时任务」，使用时钟图标。它是一级管理入口，应用页不再提供第二套任务列表或编辑界面。

列表包含：搜索、新建、全部／已启用／已暂停／已结束筛选。每行显示名称、关联会话、时间规则、下次具体执行时间、最近一次执行状态；失败或需要处理时提供明确入口。

计划状态和执行状态分开显示。例如「每天 09:00 · 已暂停」可以同时显示「上次执行中」；暂停未来触发不会取消已提交工作。“已结束”用于已消耗且没有待处理执行的一次性计划，执行结果另列，不能把失败混作成功。

点击任务进入详情，展示指令、执行时间、关联会话、执行记录和操作。首版详情沿用当前页面组件风格，不建设另一套聊天工作台。

### 2.2 创建与编辑

会话内示例：

- “30 分钟后检查这次部署的结果。”
- “每天上午 9 点整理这个项目昨天的变更。”
- “每周五下午 5 点生成本周工作总结。”

模型将自然语言转成结构化规则和完整指令。内容与时间明确时直接创建并展示结果卡；目标、日期或时区确有歧义时使用现有提问流程。不得在后端未保存成功时宣称已安排。

卡片显示任务名称、时间规则、下次日期时间和状态，提供「查看任务」「暂停／恢复」入口。卡片位于创建消息处，不占用底部子任务协作卡片，也不在每轮回复中重复插入。

菜单新建时填写名称、任务指令、时间规则，并显式选择关联会话；从会话创建则绑定发起会话。首版只绑定未归档的普通主会话，不把协作子会话变成长期定时目标。绑定后不能通过编辑悄悄更换会话，改目标需重新创建。

保存的是完整、可复查的指令；模型可依据当前对话整理必要的项目、网址和检查对象，不只保存含糊的“稍后继续”。执行仍使用关联会话的 canonical 历史，不复制整段历史为定时任务上下文。

### 2.3 执行与记录

- 每次触发按普通 user input 提交，消息可通过触发记录显示「来自定时任务」；不能改用高优先级 system 指令。
- 不打断已有执行、不插队、不 steer 其他轮次；忙碌时使用原输入队列。
- 使用提交时会话当前的模型、模式、项目和工具配置，遵守原有解析与权限规则；不因为定时执行提升模式、复制临时授权或开启 App。
- 每条记录至少显示计划时间、接收时间、开始／结束时间（实际存在时）、状态、跳过／失败原因和会话定位入口。
- 结果引用对应的 queued input、Turn 和 canonical message；不得读取“会话最后一轮”冒充该任务的结果。
- 审批、问题、流式输出和手动重试都在原会话处理。任务页只展示状态和跳转入口，不复制审批按钮或答案存储。
- 从执行记录进入原会话并定位到对应消息；尚在队列中则定位对应排队项。点击任务定义本身不会创建新会话。

## 3. 规则与边界

### 3.1 时间规则

| 规则 | 首版定义 |
| --- | --- |
| 一次性 | 保存确定 UTC 时刻及展示时区；“30 分钟后”以服务端接受创建的时间为基准计算一次，刷新不重置 |
| 每天 | IANA 时区与当地时分；下一次从日历规则计算，不从上次执行完成时间累加 |
| 每周 | IANA 时区、星期集合、当地时分；至少选择一天 |

自动采用创建时用户设备的时区；界面不显示时区，也不提供时区选择。已有任务保留保存的时区，不随设备跨时区自动改变。时间不存在的夏令时日期跳过，重复的当地时间只执行第一次对应的 UTC 时刻。

只维护一份结构化 schedule，不同时维护可独立编辑的 cron／RRULE。后端计算并返回下次时间，前端只格式化展示。修改规则增加规则版本，已经接收的执行保留其指令与规则快照。

### 3.2 操作语义

| 操作／情况 | 行为 |
| --- | --- |
| 目标会话正忙 | 按正常 submit 规则进入该会话队列 |
| 同一定时任务上次仍在排队、执行或需要用户处理 | 本周期跳过并记原因，不积累同一任务的多份输入；手动立即执行提示该任务仍在处理中 |
| 不同定时任务绑定同一会话 | 按该会话原队列顺序处理，不新增另一套并发调度 |
| 暂停 | 阻止之后接收新触发，已接收的工作继续按会话规则处理 |
| 恢复 | 周期任务从下一个未来时刻开始，不补跑暂停期间的周期 |
| 修改名称／指令／时间 | 只影响以后接收的触发；已接受指令及执行归属不变 |
| 立即执行 | 复用同一提交链路，要求幂等请求 ID；周期任务保留下次计划，一次性任务提前执行则消耗原计划，避免到时再执行一次 |
| 删除定时任务 | 停止后续触发、从正常任务列表移除；不删除会话历史，不取消已接收的工作；已接收记录保留关联以便收尾 |
| 撤回排队项／停止当前执行 | 进入原会话使用现有操作，只影响对应输入或当前 Turn；任务页不能无条件取消整个会话 |
| 关联会话归档 | 暂停其定时任务；已接受输入按原会话归档规则处理；恢复会话不自动恢复定时计划 |
| 关联会话删除 | 同步清理关联计划和触发记录，不留下会反复触发的失效目标 |

暂停、删除、编辑与到期接收的竞态以数据库事务提交次序为准。界面必须如实说明哪些工作已经提交，不能用前端关闭卡片代替停止调度。

### 3.3 休眠、退出与重启

- 本地 daemon 运行且电脑可执行时才提供调度；不承诺退出应用、关机或休眠期间准时执行。仅关闭窗口是否仍可执行取决于 daemon 和所需桌面桥接是否仍在运行，不能等同于退出应用。
- 启动／唤醒后，对离线期间尚未接受的周期跳过，转到下一未来时刻；错过的一次性任务标记「已错过」，用户可以手动执行或重新设定时间。
- 记录最近错过的时间范围、次数和原因，长时间离线不逐条制造大量聊天输入或运行记录。daemon 每秒检查一次；检测到超过 5 秒的计时中断或系统时间回拨时按离线处理，5 秒内作为计时抖动处理。时间计算集中在可测试入口。
- 已经持久化接受的触发不能又算作“错过”。重启先核对原 clientMessageID 对应的输入／Turn，再恢复原队列；不能生成新身份重投。
- 原 running Turn 仍按当前 Recover 标记中断／失败，旧审批失效。首版不恢复原工具调用栈，不自动重放已执行或副作用不确定的操作；用户在原会话显式重试。
- 需要桌面 runtime 的工具沿用现有桥接与鉴权。没有有效桥接时按原工具失败语义处理，不借用前端当前选中的会话，不自动打开并批准其他能力。

### 3.4 需要用户处理与通知

审批与必要问题复用原会话规则，等待期间不通过模型轮询进度，也不因无人处理视作批准。

执行记录的“需要输入”从原 input request 及 canonical 问答关系推导。原 Turn 已收尾但仍有未答问题时，不能仅凭 turn.completed 标成“已完成”；需关联现有 `input-flow-{requestID}` 补答身份。显式重试沿用原 retry 链。普通后续聊天不自动归入该次执行。

首版不改变问题原有的等待时长、回答、跳过及取消语义，也不新增一个任务专属等待引擎。实现时须验证未回答、已跳过、已撤回答案和补答后的展示，不能令计划因过期内存状态永久卡住；用户可通过原问题操作或暂停任务明确处理。

提供完成、失败、待审批／需答复的系统通知，点击定位原会话对应记录；不为每个 token、排队轮询或无变化快照发通知。默认成功执行结束通知一次，同一原始审批／问题只提醒一次。

系统通知由 Electron 主进程负责，不依赖任务页正在打开。操作系统禁用通知不影响执行，任务页保留状态；重启不批量补发历史成功通知。通知只是提醒，不作为任务状态或交付成功的事实源。

## 5. 数据与唯一事实源

已新增 `scheduled_tasks` 与 `scheduled_task_runs`，当前 schema 版本为 24。触发保存名称、指令和时间规则快照，执行状态从原会话推导。

| 记录 | 保存内容 |
| --- | --- |
| 定时计划 | ID、目标 sessionID、名称、完整指令、结构化 schedule、时区、启用／暂停／删除标记、定义及规则版本、调度游标和时间戳 |
| 触发记录 | ID、taskID、定义快照、来源（定时／手动）、scheduledForUTC、接收时间、唯一 clientMessageID、输入／Turn 引用；未提交前的交接状态、跳过／提交失败原因 |

排队、运行和执行结果从已有 queued inputs、turns、canonical messages 读取，不在定时表、前端 overlay 中各存一份可独立修改的执行状态。重试与补答通过真实轮次和请求关系追踪，不能用目标会话的“最新一轮”覆盖旧记录。

计划标题和指令属于明确的定时配置；会话历史仍只有 canonical messages 一份。provider profiles 与模型元数据继续来自 YAML，不复制到定时任务表形成新的配置中心。

## 6. 接收、提交与恢复

定时器位于 daemon，普通程序负责计算和唤醒；等待时间不调用模型。菜单“立即执行”和到期触发使用同一 TaskService 接收／提交链路。

1. 在事务中检查计划版本、启用状态、目标有效性与同任务未结束执行，接收一个不可变触发记录并推进调度游标。
2. 定时触发唯一身份为 `taskID + scheduleRevision + scheduledForUTC`；手动执行与创建分别要求稳定 requestID。重复相同请求返回原结果，同一身份不同内容拒绝。
3. 为触发生成一次并持久化 clientMessageID，调用现有 `Engine.Submit`，显式传目标 Session ID 与指令；不传 system kind，不走另一套执行器。
4. 持久化提交结果引用。提交已生效但回包／记录更新未完成时，按原 clientMessageID 查找 canonical input／队列／Turn，补齐关联；不能因重新解析模型失败把已执行输入当成未提交。
5. 只有确认原输入未被接收才允许以同一身份继续交接。已完成、已取消或已撤回的输入不因恢复逻辑复活；确实无法提交时如实记录失败。
6. Turn 收尾仍由 engine 原事务写入 canonical message、Turn 和 lifecycle events；定时视图引用这些事实，通知和 UI 刷新不反向决定成败。

不要求外部副作用“恰好一次”，但必须保证同一已接受触发不会因重复 tick、请求重试、重启或丢失回包创建第二条任务输入。暂停／编辑与接收的数据库仲裁、接收与 submit 之间的崩溃窗口是 M1 的重点测试对象。

## 7. API、工具和桌面状态

以下契约已在 core `contracts/` 定义；运行协议为 3：

| 操作 | 资源范围 |
| --- | --- |
| 全局列表／新建 | `GET /scheduled-tasks`、`POST /scheduled-tasks`；列表可按 sessionID 过滤，界面提供状态筛选；创建正文必须显式带目标 sessionID 与 requestID |
| 查看／修改／删除 | `/scheduled-tasks/{taskID}`；修改及状态操作校验预期 revision，不能覆盖并发编辑 |
| 立即执行／历史 | `POST /scheduled-tasks/{taskID}/runs`、`GET /scheduled-tasks/{taskID}/runs`；执行要求 requestID，历史分页 |
| 查看一次执行 | `GET /sessions/{sessionID}/scheduled-task-runs/{runID}`；验证 task、run、session 的实际归属 |
| 排队撤回／取消／审批／补答／重试 | 复用原 Session scoped API，显式携带对应 sessionID、clientMessageID、turnID 或 requestID |

Task 是自己的资源，全局列表无需虚构当前会话。所有会话业务仍使用显式 sessionID；不增加后端 focus 或全局 `/submit`、`/events`。

模型入口采用一个 `builtin_scheduled_task` 核心工具，包含 create/list/update/delete/run 动作，保持核心工具表的数量约束。简中、繁中、英文及 transcript 显示名已接入。工具只管理当前普通主会话的计划，子会话不提供该能力；全局页面由用户明确选择目标会话，不恢复跨会话委派。

菜单与已保存计划的调度不依赖 App 加载。启用状态只有计划本身一处事实源，不新增独立全局开关。

任务列表和详情读取 REST 快照，生命周期继续复用关联 Session SSE。全局页使用有界刷新；Electron 通知可集中读取增量记录，不为每个历史任务永久订阅一个 SSE，也不新增全局事件流。通知去重仅保存投递身份，不复制业务状态。

前端 Router 管理页面位置，Query 缓存服务端快照，Zustand 只存 UI 和实时 overlay；卡片、列表与详情共用同一查询。刷新或切换会话不能影响计时。

## 8. 分阶段交付与工期

按 1 名熟悉两仓的开发者估算，完整首版 **8–12 个工作日**；第一批仅一次性任务 **5–7 个工作日**，第二批在相同链路补每天／每周重复。此估算包含本地完整验收，不含正式签名、公证、发布与额外范围。

| 阶段 | 交付内容 | 完成条件 |
| --- | --- | --- |
| M1 数据与调度 | 定义／触发记录、迁移、一次性计算、接收幂等、submit／恢复对账、工具接入选型 | 两种 store 语义一致；重复／崩溃／取消不双投；确定补答与重试关联方式 |
| M2 一次性完整体验 | 独立菜单、详情编辑、自然语言创建、消息卡、立即执行、通知及会话定位 | 第一条端到端场景通过；暂停删除、队列、审批、错过与重启行为完整，形成第一批验收 |
| M3 重复计划 | 每天／每周、时区、暂停恢复、忙碌跳过、休眠补账 | DST、时钟变化与跨日测试通过，不积压旧周期；不另建调度或执行路径 |
| M4 整体验收 | 两仓回归、旧库迁移、真实源码 Electron、锁定 core 精确提交 | 下方验收项全部通过；删除临时补丁与旧路径；记录实际验证及限制 |

工时构成参考：后端 3–4 天，桌面管理界面 2–3 天，会话工具／卡片／通知接入 1–2 天，联调验收 2–3 天。阶段之间存在交叉，不将两张表重复相加。

## 9. 验收清单

第一条真实场景：“30 分钟后检查这次部署的结果”。在隔离环境设置较短延迟，验证聊天创建、列表可见、按时提交、原会话结果和通知；自动化测试使用可控时钟，不真实等待 30 分钟。

- [ ] 聊天和菜单都能创建同一结构的任务；重复提交不创建两份，失败不显示已创建。
- [ ] 卡片、列表、详情的规则／状态一致；刷新、换页、关闭任务页不影响调度。
- [ ] 到期只产生一个真实输入；目标忙碌时正确排队，不打断、不插队。
- [ ] 暂停／删除与到期并发时，按接受边界处理；已经接收的工作仍可从原会话追踪。
- [ ] 定时任务自身忙碌时跳过下一周期；同会话的普通工作继续使用原队列。
- [ ] 审批和问题只在原会话处理；无答案不视作批准；迟到补答、撤回答案、跳过问题、显式重试不串到其他轮次。
- [ ] 执行记录能定位确切输入／结果，后续普通聊天不会改写旧记录；已提交不显示为已完成。
- [ ] 每天／每周、DST 跳时与重复时、跨时区设备、时钟回拨不重复触发；修改规则只影响未来接受的执行。
- [ ] 休眠／退出错过有可见原因，一次性可手动处理，周期不补跑积压。
- [ ] 接受前、submit 前、submit 后未记回包等崩溃点均完成对账；运行中重启如实中断，不重放工具。
- [ ] 归档、恢复、删除会话不留下失效调度；删除计划保留已经产生的聊天记录。
- [ ] 完成／失败／需要处理通知能够定位，重复读取不重复提醒；系统禁用通知时状态仍可查看。
- [ ] 旧数据库迁移保留会话和消息，失败回滚，重启后计划／游标／关联仍在。
- [ ] 基础协作卡片、普通会话、模型配置、审批、输入队列和重试没有行为回归。
