# 截图预算策略：实现与三组实测

日期：2026-11-06。结论：**本次新策略恢复了缓存命中、降低了估算费用，但没有改善实测延迟。** 数值只是工程初值，尚未证明为最优预算。

## 已实现的行为

- 取消每到第 9、15 张自动执行的 8→3 淘汰，Builder 和工具循环只应用已提交的清理位置。
- 统一请求预算检查控制自动截图与 `media_read(purpose=observation)`：估算图片 token 上限为 `min(32,768, 窗口 × 10%)`；窗口未知时取 32,768；图片 base64 编码体积上限 16 MiB。这不是精确视觉计费或完整 HTTP 请求上限。
- 超限后按时间清理到两项预算的一半，至少留下最新一张；最后一张本身超限时明确报错。平时新增截图不推进位置。
- 文本冷却或 Compact 本来就要改写历史时，一并将自动截图清至最近三张；预算更紧时可更少。冷却通过同一 CAS 提交，Compact 与摘要、新 epoch 的图片位置通过同一事务提交；候选失败不保存清理结果。
- SQLite schema v60 保存 `image_through_id`，由输入轮、工具调用、附件 key 组成，防止回读同一附件或重用其他轮的调用 ID 时误删新观察。查找位置先于工具过滤，避免边界图被过滤后旧图复活。关闭文本冷却不恢复已省略的图片。
- 原图、缩图规则和回读入口保留；参考图及用户上传不参与自动截图淘汰，仍受整体上下文预算和 Compact 影响。

## 同轮三组结果

模型为 BuzzHive 网关配置的 DeepSeek Flash，Responses 协议。每组 12 次，共 **36 次真实调用，无失败或重试**。

| 指标 | 全部保留 | 旧 8→3 | 新预算策略 |
| --- | ---: | ---: | ---: |
| 输入 token，含缓存 | 449,292 | 433,296 | 449,268 |
| 缓存输入 token | 381,312 | 325,760 | 381,312 |
| 未缓存输入 token | 67,980 | 107,536 | 67,956 |
| 输入缓存命中率，token 加权 | 84.87% | 75.18% | **84.87%** |
| 累计传入图片次数 | 78 | 54 | 78 |
| 单次最多图片数 | 12 | 8 | 12 |
| 估算费用 USD | $0.011348 | $0.017115 | **$0.011345** |
| 平均首字延迟 | 1.224 秒 | **1.124 秒** | 1.463 秒 |
| 首字延迟中位数 | 1.306 秒 | **1.144 秒** | 1.554 秒 |
| 平均总耗时 | 1.286 秒 | **1.186 秒** | 1.539 秒 |

相对本轮旧策略，新策略命中率提高 **9.69 个百分点**、估算费用降低 **33.7%**，平均首字延迟增加 **30.1%**。第 9 张时旧策略发生淘汰，命中率降至约 4.1%，新策略和全部保留组仍约 89.3%。

新策略与全部保留组的图片、历史内容基本相同，用量差异只有缓存隔离串产生的少量 token，但平均首字延迟仍相差约 0.239 秒。这说明本次存在网关、网络或服务调度噪声；不能把全部延迟差异归因于图片数量，更不能宣称新策略会提速。

全部调用在 UTC 04:24–04:26 非高峰时段。[官方单价](https://api-docs.deepseek.com/quick_start/pricing/)每百万 token 为缓存输入 $0.003、未缓存输入 $0.15、输出 $0.6；三组各输出 12 token。本轮合计估算 **$0.03981**，来自真实 usage，**不是 BuzzHive 实扣账单**。

## 测试方法与适用范围

- 复用[上轮](screenshot-cache-benchmark.md)前 12 张内容哈希不同的已保存截图及相同合成长文本，每张经真实截图缩图函数转为 1401×856。三组分支采用独立固定隔离前缀，每步轮换调用顺序，防止相互预热和固定先后偏差。
- 调用真实新预算规划与投影函数；旧 8→3 仅作为测试文件里的冻结基线。历史始终从同一素材追加，每次返回 `OK` 后追加实际回复。关闭推理，最大输出 32 token，无工具执行；计时含请求编码、上传和网关等待，不含预先准备图片的时间。
- **本次 12 张图片未超新预算，也未触发冷却或 Compact。** 本次验证的是“不需要清理时，不再因固定张数破坏缓存”，不是清理发生后不会损失缓存。超预算清理、持久化、冷却及 Compact 合并另由下述本地回归测试验证；没有测其真实账单成本。
- 只有一条 12 步轨迹、每组一次运行，无显著性检验；不代表所有模型、长时间缓存、图片密集任务或 xhigh 推理任务。不能把上轮 18 次与本轮 12 次的总量直接比较。
