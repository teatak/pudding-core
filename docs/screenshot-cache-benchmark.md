# 截图淘汰与缓存：DeepSeek Flash 实测

这是旧 8→3 机制的历史实测；当前实现和三组复测见 [预算策略复测](screenshot-budget-benchmark.md)。

日期：2026-11-06。结论：**8→3 在本次长工具文本场景中减少图片和延迟，但增加估算费用，不能作为已验证的省钱策略。** 本次未更改产品阈值。

## 结果

通过当前配置的 BuzzHive 网关，使用 `deepseek-flash`、Responses 协议完成 36 次真实请求，每组 18 次，无失败或重试。

第 9 张时，前六张变成文字占位；最早改变的位置之后，保留的工具文本也失去原有缓存。第 15 张时，前六张的占位已稳定，较早前缀仍能命中，变化发生在第七张附近。下一次追加请求的缓存恢复，符合[官方前缀缓存规则](https://api-docs.deepseek.com/guides/kv_cache/)。

## 方法和边界

- 使用同一组 18 张已保存、内容哈希不同的浏览器截图。通过真实 `ScreenshotForProvider` 转为 1401×856，两组完全相同；临时附件目录隔离，不修改原图、线上会话或磁盘缓存。
- 以约 2,000 token 的固定文字开头，每步追加截图及约 4,700 token 的合成工具记录，再追加模型返回的 `OK`。这用于测量截图与长文本交错时的缓存损失，不是完整业务任务回放。
- 淘汰组调用真实 `LimitToolImages`，基线不淘汰。每个分支使用独立固定隔离前缀，防止互相预热；隔离串会产生几个 token 的细微差异。每步交换先后顺序，串行执行，不额外等待缓存写入。
- 关闭推理，输出上限 32 token；没有可执行工具，也不检查浏览操作或任务正确率。与平时的 xhigh 推理模式不同，结论只涉及输入缓存和本次短输出延迟。
- 延迟从调用 provider 到首个正文 token／流结束，包含组装请求、上传和网关耗时，不包含预先准备图片的时间。不能将差值全部归因于模型推理或缓存。
- 一条 18 步轨迹、一次对照，没有重复试验或显著性检验。未测试其他模型、截图为主的轨迹、26→3 等阈值、长时缓存淘汰、回读成本或原 2048 分辨率。
- 原计划 144 次被自动审批以费用及截图发送规模过大拒绝，缩小为上述 36 次后获准执行。执行器限制最多 36 次请求，累计输入超过 200 万时停止后续请求；它不是精确计费硬上限。

## 对当前策略的判断

固定 8→3 可作为视觉上下文上限，能限制图片数量，本次延迟也更低；但不能同时承诺降低费用。尤其在图片后积累了较多文本时，降低缓存命中带来的重算成本可能高于删图收益。

后续应优先验证：在有足够预算时保持历史前缀稳定，将图片清理与文本冷却／Compact 等本来就会改写前缀的时机合并；保留独立图片上限处理超预算情况。不能只根据本次结果把阈值调大并断言更省钱。参考图仍应与自动截图分开管理。

## 复现与证据

执行器：[tool_images_live_test.go](../internal/contextbuilder/tool_images_live_test.go)。默认跳过，必须显式设置 `PUDDING_IMAGE_EVAL_LIVE=1`，并提供 `HOME`、`PROFILE`、`MODEL`、`MANIFEST`、`REPORT`（均带 `PUDDING_IMAGE_EVAL_` 前缀）。`MANIFEST` 是本地图片绝对路径组成的 JSON 数组，`REPORT` 是输出 JSON 路径；该操作会产生模型费用并把图片发送给所选 provider。

历史执行器参数：`STEPS=18`、`REPEATS=1`、`WORKLOAD=text_tail`。当前执行器已加入第三组，默认每组 12 次、总计 36 次，不再使用此旧参数组合。历史命令：`go test ./internal/contextbuilder -run '^TestToolImageCacheLiveEvaluation$' -v -count=1 -timeout=15m`，按项目要求配置 Go、abseil 环境。

[逐请求用量、延迟与汇总](validation/screenshot-cache-deepseek-2026-11-06.json)不包含图片像素、源文件路径、凭据或业务文本。
