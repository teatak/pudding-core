# Unified Canvas resource contract

Protocol 7 supports React source canvases under `/canvases`. The release upgrade from schema v24 to final v25 converts structured content into editable source packages and creates the source-canvas tables in one transaction. Development-only v25–v28 migrations are not shipped. The resource keeps one source/revision store with session mounts that carry no content copies. Shared client schemas and limits live in `contracts/canvas.ts` and `contracts/canvas.json`. Desktop product behavior and acceptance records live in its `docs/canvases.md`.

A canvas has an integer optimistic `revision`, immutable `headRevision` / `activeRevision` source hashes, optional `sourceSessionID`, source-slot bindings and `bindingVersion`. Deleting the origin session clears the provenance link without deleting the canvas. Source files are atomically installed under `<home>/canvases/<id>/revisions/<hash>` before SQLite records the reference. Failed saves cannot overwrite the active source.

Every revision references an immutable source package; new activation requests require a matching build receipt. Saves accept `package` only; revision reads return `kind: app`, `package` and `manifest`. No structured content writer, layout writer or alternate renderer remains.

Migration v25 deterministically converts Markdown, tables, charts (bar/line/area/pie/donut), galleries, timelines and grids (including metrics) to editable React/CSS source. Read-only forms are retained too. The resource ID, name, timestamps, existing active selection, session mounts, favorites and recent references survive; dirty copies remain separate resources. The v24 release stored only its current content and a revision counter, so migration does not invent past versions. Generated helpers live inside each source package, not a legacy runtime. Markdown is parsed with GFM support without enabling raw HTML execution.

Referenced image attachments and public HTTP(S) images are embedded as data URLs for the existing sandbox. Public fetches use no credentials or proxy, reject private/loopback addresses and redirects to them, and have bounded time/size. An image that cannot be embedded (a deleted attachment, an unreachable or non-image URL, an oversized file, a gallery item without a source) becomes a placeholder that keeps its alt text and caption, so one lost image cannot stop the upgrade and the app from starting. Unsupported canvas content still aborts the upgrade and leaves the old database intact. Source directories are atomically published before the SQL commit; retries reuse identical packages. Whole-database migration backups remain. No canvas archive management API or UI remains.

Migration carries the previous active selection to its converted source hash without fabricating a build receipt; opening that selection performs the normal real TypeScript/build checks. Later edits still require the ordinary preview/inspect/activate workflow. Development snapshots produced by the abandoned archive migration can be restored with the separate `scripts/restore-canvas-dev` command, after validation against a copied database; this recovery is not part of daemon startup.

Routes (all require the existing loopback startup token):

- `GET/POST /canvases`, `GET/DELETE /canvases/{id}`.
- `POST/GET /canvases/{id}/draft` starts or reads the persistent working copy, initialized from the current source head. `GET/PUT /canvases/{id}/draft/file` reads or edits one file; writes require the previous `draftHash`, and `null` deletes. An incomplete draft is allowed. `POST /canvases/{id}/draft/commit` validates the complete package, publishes one immutable revision and advances the source head only when it still matches the draft's base. Draft conflicts return `currentDraftHash`; source conflicts return `currentRevision` and `currentHeadRevision`. `GET /canvases/{id}/revisions` and `GET /canvases/{id}/revisions/{hash}` expose committed versions. Drafts live under `<home>/canvases/<id>/draft`.
- `POST /canvases/{id}/build-receipts`, `POST /canvases/{id}/activate`.
- `PUT /canvases/{id}/bindings`.
- `POST /canvases/{id}/queries/{operationID}`.
- `POST /canvases/{id}/actions/{operationID}/prepare`, `POST /canvases/{id}/action-runs/{actionID}/execute`, `GET /canvases/{id}/actions`.
- `GET/POST /canvases/{id}/links`, `DELETE /canvases/{id}/links/{linkID}`.

`POST /sessions/{id}/canvases/{canvasID}/open` opens or reuses a session reference. The session `/canvas/items` API lists resource references. Its former POST/PUT/PATCH writers are removed. Removing an item removes only its mount. Global deletion removes the resource from all views. The old `/workbenches`, `/canvas/saved`, and `/canvas/items/{id}/save` routes are absent. Library `savedItemID` now references the canonical resource, not a separate saved-content table.

Queries validate the exact saved operation, parameter schema, and current installed App connection. A unique usable connection is selected automatically; multiple usable connections require an explicit canvas binding. No per-query authorization is stored. Automatic queries require both a `read` effect hint and read-only transport semantics (REST GET without body, or a GraphQL query). A generated `effectHint` alone never grants write access. Only declared parameters are substituted; no server-side generated code is evaluated. REST and GraphQL share `internal/appexec` with session tools, whose original session/mode gates remain intact. Canvas requests cannot override connection-owned query/body fields.

Actions additionally require the installed endpoint to declare `canvas_writes: true` (default false). This field does not elevate upstream account permissions. Prepare freezes account, source, operation, validated input and resource revision. Execute requires explicit host confirmation, revalidates the context and claims the prepared record transactionally. Repeated confirmations return the existing run; a changed context returns a conflict. Transport ambiguity is `unknown`, and store startup changes unfinished `executing` runs to `unknown`. No automatic replay occurs. Deterministic failures before dispatch are `failed`. Query refreshes cannot overwrite the recorded action result.

Entity links retain both App and connection IDs. Local link writes require explicit confirmation and the current resource revision. Changing a binding does not retarget existing links to a new account. Source App data remains external; cached query results are not persisted as business facts.

Canvas HTTP does not create synthetic sessions or globally reuse MCP transports. Authoring tools are provided by the single Desktop `canvas` App; source creation/build/activation require Code mode, while resource discovery, reading and opening are available in Chat mode. All tools use explicit session routing; user-requested agent analysis uses ordinary session submit/cancel/events.

The sandbox runtime uses the same Canvas source format and does not introduce a second resource lifecycle. Published migrations through v24 remain intact; only the final v25 canvas upgrade follows them. Development data from intermediate layouts is converted locally and is not handled by the release migration.
